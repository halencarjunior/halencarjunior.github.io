dz6-mcp: Bringing a Terminal Hex Editor to AI Agents

A look at the dz6 editor by Mente Binaria and the MCP server I built to make its byte-level workflows available to AI assistants.

Oct 19, 2026Humberto Jr (bt0)infosec / tools

When I inspect an unfamiliar executable, I want the exact bytes to stay close to the analysis. An assistant can summarize a PE header or point me toward a suspicious section, but it needs a reliable way to read offsets, inspect structures and verify what is actually on disk. That was the motivation for dz6-mcp, an MCP server I developed around dz6 by Mente Binaria.

The two projects have distinct roles. dz6 remains the interactive terminal hex editor. dz6-mcp exposes its engine as structured tools that an MCP client can call. The server does not perform autonomous reverse engineering: it gives an agent access to bytes, parsed metadata, searches and controlled edits, while the analyst evaluates the results.

What dz6 Provides

dz6 is a fast, Vim-inspired hex editor for the terminal. Its TUI can navigate large files, edit hex or ASCII, search text and byte patterns, inspect strings, and attach comments, bookmarks and colored blocks. It also parses basic PE and ELF headers. For an analyst working by hand, these features put file structure and individual bytes in one place.

The upstream command line is straightforward: dz6 --readonly sample.bin opens a file without editing it; dz6 --offset 400 sample.bin starts at an offset, interpreted as hexadecimal by default. Inside the editor, searches, bookmarks and the header view help move between raw data and executable structure. The dz6 README documents its command line and key bindings.

What the MCP Server Adds

dz6-mcp runs locally and speaks JSON-RPC over standard input and output. It reuses dz6 as a Rust library rather than scripting the TUI. Each MCP session can keep multiple files open; a tool call containing a path opens that file lazily and reuses its state on later calls. Protocol messages use stdout, while diagnostics go to stderr.

The current server advertises 39 tools. They cover file state, byte and string reads, search, signature scanning, PE/ELF inspection, address translation, staged editing, annotations and diagnostics. The table shows where the TUI and the MCP layer meet.

Taskdz6 TUIdz6-mcp
Inspect bytesNavigate the hex and text viewsread_bytes, read_int, read_string
Find evidenceInteractive text/hex search and string listsearch, search_all, pattern_scan, strings
Understand executablesPE/ELF header viewheaders, sections, symbols, pe_info, elf_info
Navigate addressesJump to offsets and header fieldsaddress_translate, read_at_address
Record findingsComments, bookmarks and colored blocksAnnotation tools that share the .dz6 sidecar
Change bytesInteractive editing and write commandswrite_bytes, fill, undo, save

For PE and ELF work, the MCP layer goes further than a raw hex dump: it can return sections and symbols, translate virtual addresses to file offsets, inspect PE imports and metadata, or report ELF interpreter, dependencies and notes. Signature scanning supports named patterns with byte and nibble wildcards, gaps and alternation. These are useful for triage; any interpretation still needs validation against the original file and other analysis tools.

Build and Connect

The current release builds against a sibling checkout of dz6. Upstream dz6 is currently a binary crate; dz6-mcp includes a patch that exposes its modules as a library and keeps terminal output away from the MCP protocol stream. The patch is tied to the dz6 commit shown below. Use fresh sibling checkouts and check the project README for changes before building.

git clone https://github.com/halencarjunior/dz6-mcp.git
git clone https://github.com/mentebinaria/dz6.git
git -C dz6 checkout --detach 9612897db2b0c5ec75ea92285b183e1062ba9af9
git -C dz6 apply --check ../dz6-mcp/patches/dz6-library.patch
git -C dz6 apply ../dz6-mcp/patches/dz6-library.patch
cd dz6-mcp
cargo build --release --locked

The README specifies Rust 1.89 or newer. The MCP client's command must point to the built executable, not its parent directory. A minimal read-oriented client configuration is:

{
  "mcpServers": {
    "dz6": {
      "command": "/absolute/path/to/dz6-mcp/target/release/dz6-mcp",
      "args": ["--readonly"]
    }
  }
}

Client configuration formats vary. The repository documents setups for several harnesses, including Codex, Claude, OpenCode and generic MCP clients. Reconnect the client after changing the binary or its tool list.

A Practical Triage Session

Suppose an unknown file arrives as /samples/unknown.bin. I would begin with bounded, read-only calls and let the evidence determine the next step. These are example MCP tool calls, not output from a tested sample:

file_info    {"path":"/samples/unknown.bin"}
read_bytes   {"path":"/samples/unknown.bin","offset":0,"length":128}
analyze      {"path":"/samples/unknown.bin"}
strings      {"path":"/samples/unknown.bin","min_length":6,"max":100}
pattern_scan {"path":"/samples/unknown.bin","patterns":[
  {"name":"pe-mz","pattern":"4D5A"},
  {"name":"elf","pattern":"7F454C46"}
]}

If the file is a valid PE or ELF executable, I can ask for sections and the matching pe_info or elf_info. A section with unusual entropy is a lead, not proof of packing or encryption. If a disassembler reports a virtual address, address_translate maps it to a file offset, and read_at_address verifies the bytes there. On a malformed file, the raw read and search tools remain useful even if structural parsing fails.

For a controlled patch on a copy, write_bytes stages changes in memory. read_bytes then shows the proposed bytes, undo can reverse them, and save writes them to disk. Comments and bookmarks persist in the same <file>.dz6 TOML sidecar used by the TUI. The documented workflows include PE and ELF triage, signature scanning and patch verification.

Important Boundaries

The server is a local file tool, so its permissions follow the process that runs it. It has no path sandbox. --readonly sets the default for opening documents, but a client can request open_file with readonly: false; dump can still write a separate output file. Run it with a least-privilege account, use copies of important samples and review a client's tool permissions before granting edit access.

Edits are visible to byte reads, search, pattern scans and entropy analysis before save. Structural parsers and the strings tool inspect the on-disk mapping, so they do not reflect staged edits until a save or reopen. truncate is different again: it changes the file immediately and cannot be undone. save does not create a backup. These behaviors are documented in the project's core concepts and security notes.

Finally, bytes and extracted strings are untrusted data. A file may contain text that looks like instructions for an AI assistant. Treat it as sample content, not as a command to execute or a policy to follow.

Where It Fits

dz6 is the hands-on editor I can use to inspect and annotate a file in the terminal. dz6-mcp makes the same underlying work available as structured operations inside an agent workflow. That pairing is especially useful when an investigation moves repeatedly between hypotheses, exact offsets and reproducible evidence. The agent can help organize the process; the bytes, the analyst and the explicit save step remain the source of truth.
